## 1. 기존 GAMELOG `reviews` 테이블

제공된 운영 카탈로그 결과로 `public.reviews`가 존재하며 RLS가 켜져 있고, `reviews.user_id`는 `auth.users(id)`를 참조하는 `ON DELETE CASCADE` 외래 키다. 따라서 해당 Auth 사용자를 삭제하면 그 사용자의 게임 리뷰도 연쇄 삭제될 수 있다. 이번 검토에서는 행 수·실제 리뷰 데이터는 조회하거나 수정하지 않았다.

개발 브랜치의 앱/컴포넌트/라이브러리/테스트/현재 마이그레이션을 검색한 결과, 운영 LIKE TURTLE 기능에서 `reviews`를 사용하는 호출은 찾지 못했다. `supabase/schema.sql`에는 과거 GAMELOG 스키마 정의가 남아 있다. 즉 “현재 앱의 사용 여부”는 검색상 미사용이지만, 운영 테이블 자체가 비어 있거나 폐기 가능하다는 뜻은 아니다. Auth 삭제의 현재 cascade 대상에 포함되는 데이터로 다뤄야 한다. 일반 탈퇴 이외의 관리자/Auth 삭제 경로도 이 제약의 영향을 받으므로 별도 정책과 복구 책임을 정해야 한다.

## 2. 차단 회원: 직접 API와 상세 페이지

현재 `008_blocked_content_rls.sql`은 인증된 요청에 차단 관계를 적용한다. 차단한 회원의 게시글과 댓글은 PostgREST 직접 SELECT에서 숨기고, 작성자 닉네임을 반환하는 SECURITY DEFINER RPC도 같은 필터를 적용한다. 본인 알림은 연결된 댓글이 보이는 경우에만 조회되도록 제한한다. 상세 페이지는 같은 RLS 대상 게시글 조회를 사용하므로 직접 API와 동일하게 빈 결과가 되고, UI는 존재하지 않거나 삭제된 게시글과 같은 안내를 표시한다.

비회원 정책은 별도 `anon` SELECT 정책으로 `USING (true)`를 유지한다. 차단은 차단한 로그인 회원의 화면/직접 API에만 적용하며, 공개 게시글의 비회원 열람은 보존한다. CI #78에서 직접 PostgREST/RPC 차단과 비회원 게시글·댓글·닉네임 공개 조회가 통과했다. **008은 개발 브랜치의 신규 마이그레이션이며 운영 DB에 적용되지 않았다.** 운영 정책은 게시글/댓글/알림에서 차단 방향을 동일하게 적용할 것을 권고한다.

## 3. 무료 범위 백업·복원 및 리허설

무료 요금제에는 자동 일일 백업이 포함되지 않을 수 있고, 데이터베이스 dump는 Storage 객체의 파일 바이트를 포함하지 않는다. CLI DB dump는 관리형 `auth`와 `storage` 스키마를 제외하므로, 별도 백업과 복구 절차가 필요하다. 자세한 범위는 [Supabase 무료 플랜 백업 FAQ](https://supabase.com/kb/faqs/platform/free-plan-backups), [백업 안내](https://supabase.com/docs/guides/platform/backups), [CLI db dump 참조](https://supabase.com/docs/reference/cli/supabase-config)를 기준으로 확인한다.

개발 브랜치에는 합성 데이터 전용 복구 리허설이 추가됐다. GitHub Actions의 격리 로컬 Supabase 프로젝트에서 사용자 정의 DB 스키마/행을 CLI dump로 내보내고, 별도 새 프로젝트로 복원하며, 합성 Auth 사용자는 Admin API로 새 ID와 테스트 비밀번호를 부여해 재생성하고, Storage API로 합성 파일을 내려받아 비교한 뒤 새 프로젝트에 올려 바이트를 비교한다. 실행기는 loopback URL만 허용한다. 이로써 실제 운영 데이터를 읽거나 내보내지 않는다.

**리허설 결과:** CI #78 성공. 첫 로컬 Supabase 스택에서 `recovery_probe` 합성 스키마/행을 CLI dump로 내보내고 새 두 번째 로컬 스택에 schema/data를 적용했다. Auth Admin API로 합성 계정 메타데이터를 재생성하고 Storage API로 합성 비공개 파일을 복원한 뒤 파일 바이트 비교 및 새 비밀번호 sign-in을 통과했다. 이는 합성 데이터의 격리 복원 증거다. Auth 비밀번호 해시, 기존 세션/JWT, 실제 ID/연결 관계의 완전 복원은 증명하지 않는다. Auth 사용자를 재생성하면 UUID가 바뀔 수 있어 DB 참조와 Storage 경로를 함께 매핑해야 한다. 운영 데이터의 실제 복원이나 RPO/RTO는 검증되지 않았다.

운영 복구 준비 권고:
1. 앱 DB 스키마와 데이터는 정기적으로 CLI dump하여 별도 접근통제·암호화된 보관소에 저장한다. 비밀키와 실데이터를 Git 저장소/CI 로그/일반 workflow artifact에 넣지 않는다.
2. Auth 메타데이터와 Storage 객체/버킷 설정은 DB dump와 분리해 내보내고, Storage는 파일 경로·크기·해시 manifest를 둔다. 이메일/개인정보가 포함된 백업에는 최소 접근권한과 보존기간을 둔다.
3. 같은 프로젝트에 덮어쓰기 전에 새 격리 프로젝트로 복원하고, 스키마/RLS/RPC/제약, 합성 로그인, 파일 해시, 앱 smoke test를 확인한다. Supabase 무료 호스팅에 추가 프로젝트나 보관 공간/트래픽 제한이 있을 수 있으므로 비용 없는 범위 확인이 필요하다.
4. DB/Auth/Storage 복구는 서로 다른 시점 자료를 섞지 않도록 한 복구 시점 manifest로 묶는다. 파일 자체의 복구와 메타데이터 참조 복구를 함께 검증한다.

## 4. 탈퇴·Storage·세션의 잔존 위험

운영 메타데이터에는 `storage.objects`의 statement-level BEFORE DELETE 트리거 `protect_objects_delete`가 `storage.protect_delete()`를 실행한다고 나타난다. 운영 함수 본문은 제공된 조회 결과에 없으며, 운영의 실제 Storage API DELETE 경로에서 이 트리거가 어떤 경우를 거부하는지는 직접 실행되지 않았다. 표준 Supabase Storage API 삭제는 격리 CI에서 시험했지만 운영 버전 호환성은 미검증이다. **DB SQL로 Storage 메타데이터를 직접 DELETE하지 않는다.** 운영 적용 전 별도 읽기 전용 조회로 함수 정의/소유자/권한을 확인하고, 필요하면 비운영 프로젝트에서 같은 Storage 버전/API 동작을 검증한다.

탈퇴 시작 후 개발 마이그레이션은 앱 데이터 변경을 막지만, 기존 Supabase access JWT는 만료 시각까지 유효할 수 있다. DB 쓰기는 RLS/가드로 거부될 수 있어도 세션 자체를 즉시 무효화하는 것과 같지 않으며, Storage/공개 읽기/RPC 등 모든 요청의 중단을 보장한다고 볼 수 없다. 알림 `read_at` 수정처럼 별도 권한 경로도 운영 반영 전 확인이 필요하다. 재시도는 개인정보 익명화 후 Storage 삭제/Auth 삭제 순서이며, Storage 삭제 성공 뒤 Auth 삭제가 실패하면 사진은 일부 또는 전부 없지만 계정은 남을 수 있다. 파일 백업 없이는 해당 바이트 복구가 불가능하다. 자동 탈퇴를 켜기 전에 재시도 가능한 상태 표시, 관리자 지원 절차, 사진 복구 불가 고지 및 JWT 만료까지의 접근정책을 결정해야 한다.

## 5. 운영 메타데이터 호환성 요약

운영자가 제공한 읽기 전용 catalog JSON으로 다음을 대조했다.

- 대상 주요 테이블에는 RLS가 활성화되어 있다.
- `tortoise_posts.author_id`와 `tortoise_comments.author_id`는 Auth FK이며 기존 제약 정의에서는 삭제 동작이 명시되지 않아 기본 NO ACTION 동작이다. 006의 작성자 NULL 익명화는 두 열이 nullable이고, 제공된 `validate_tortoise_reply()` UPDATE 경로는 `parent_id`/ `post_id` 연결만 고정하므로 작성자/닉네임/내용 익명화와 충돌하지 않는다.
- 답글 parent/post 삭제 cascade, 좋아요·성장·거북이·알림·고정글 FK cascade 등이 확인됐다. 다른 회원의 댓글/답글을 보존하려면 게시글과 댓글 행을 삭제하지 않고 작성자 개인정보만 익명화해야 한다.
- 알림 RLS는 본인 행 SELECT와 `read_at` UPDATE 정책이며 열별 권한 결과도 제공됐다. 관리자 게시글/댓글/고정글 정책의 관리자 계정 조건은 SECURITY DEFINER 관리자 RPC의 UID 조건과 일치한다고 제공 자료에서 확인됐다.
- 기존 댓글 알림 AFTER INSERT 트리거와 reply validation 트리거가 존재한다. 제공된 validation 함수는 익명화 UPDATE를 허용한다.
- 운영 Storage 정책, 공개/비공개 버킷 및 파일 크기 제한이 확인됐다. 001~007의 운영 호환성 검토는 과거 CI #34 등 개발 검증에 더해 제공된 운영 메타데이터를 기준으로 갱신했다. 008은 이번 개발 추가분으로 운영 적용 전 격리 CI에서 검증한다.
- `storage.protect_delete()` 본문과 실제 운영 함수 실행 결과는 확보되지 않았다. 운영 DB/RPC/트리거를 변경하지 않았고 운영에서 탈퇴/삭제 시험도 하지 않았다.

## 6.1. CI #73~#77 실패와 시정

CI #73~#77은 통합 회귀 테스트에서 실패했다. #78 로그에서 원인을 확인했다. 차단된 회원의 알림은 RLS로 숨겨져야 하는데, 테스트가 차단 설정 뒤 같은 알림의 `read_at` 갱신 결과를 단건 조회하려 해 PostgREST `PGRST116`(0행)으로 실패했다. `read_at` 소유자 권한 검증을 차단 관계 설정 전에 수행하고, 차단 후 직접 알림 조회가 빈 결과인지 확인하도록 테스트 순서를 분리했다. CI #78에서 통과했다.

#78 격리 회귀 결과: 직접 PostgREST/RPC 차단 및 anon 공개 접근, 관리자/회원 분리, 게시글 CRUD, 댓글/답글 알림, 좋아요, 검색/정렬/페이지네이션, 성장 기록·사진 CRUD, 탈퇴 사전준비, 동시 업로드, Storage 실패 후 Auth 보존 및 재시도, 타 회원 답글/사진 보존, 모바일 가입/동의·프로필과 관리자 접근거부, 데스크톱 비밀번호 재설정/로그인, 합성 DB/Auth/Storage 새 프로젝트 복구가 통과했다. Storage image pull 중 ECR rate limit 재시도가 있었지만 컨테이너 pull과 테스트는 완료했다.

운영 반영 체크리스트:
- [ ] Supabase 무료 플랜의 백업/복원 가능 범위, 저장 공간, 프로젝트 수, 보존 기간을 확인한다.
- [ ] 운영 Storage 보호 함수 본문과 소유자/권한을 비밀값·회원행 없이 조회하고, 비운영 환경에서 Storage API DELETE 동작을 검증한다.
- [ ] 정책 결정(아래)을 확정하고 privacy/terms/support 절차와 사용자 안내에 반영한다.
- [ ] 개발 브랜치 최종 커밋의 CI가 통과하고 복구 리허설 로그가 모두 성공했는지 확인한다.
- [ ] 운영과 분리된 백업/복원 지점을 만든 뒤 001~008 적용 계획을 다시 검토한다. 실제 적용은 별도 승인과 운영 창구 지정 후에만 진행한다.
- [ ] 적용 실패 시 앱 배포를 멈추고 Vercel 코드는 이전 배포로 되돌릴 수 있으나, DB 익명화나 Storage 파일 삭제는 코드 롤백으로 복구되지 않는다는 점을 운영 절차에 명시한다.
- [ ] 자동 탈퇴는 별도 승인 후에만 활성화하며, 실패/재시도 큐와 담당자 알림을 먼저 준비한다.

## 7. 사용자 결정이 필요한 운영정책 — 권고안

1. **GAMELOG 리뷰 보존:** 권고는 탈퇴 시 Auth FK에 따라 해당 계정의 과거 게임 리뷰도 삭제된다는 점을 데이터 보존 정책에 명시하고, 서비스 운영자가 데이터 목적상 유지할 필요가 있는지 결정하는 것이다. 현 FK가 cascade이므로 보존을 택한다면 별도의 승인된 스키마 설계가 필요하다.
2. **차단 범위:** 권고는 차단한 로그인 회원에게만 상대 게시글/댓글/댓글 알림을 숨기고, 비회원에게 공개 게시물은 계속 공개하는 것이다. 차단당한 회원의 공개 콘텐츠를 전역 삭제/비공개 처리하는 정책은 적용하지 않는다.
3. **탈퇴 시 커뮤니티 기록:** 권고는 게시글과 댓글/답글은 남기되 작성자 ID·닉네임·본문의 개인정보를 비식별화하고, 다른 회원의 댓글/답글과 사진은 보존하는 현재 개인정보 우선 방식을 유지하는 것이다.
4. **사진 삭제 후 Auth 삭제 실패:** 권고는 사진 삭제 결과를 재시도 상태로 저장하고 운영자에게 알리며, “계정은 남고 사진은 일부 제거됐을 수 있음”을 지원 절차에 명시하는 것이다. 사용자가 사진 복원을 요구할 수 있으면 삭제 전에 파일 백업이 성공해야 완료 상태로 전환하는 정책을 선택한다.
5. **보유·백업 기간:** 권고는 신고/차단·탈퇴 작업 감사 데이터와 백업 속 개인정보의 보관 목적·기간·삭제 시점을 구체화하는 것이다. 현재 백업 보존/실제 법률 준수에 대한 판단은 하지 않았다.
6. **세션 중단:** 권고는 탈퇴 시작 즉시 앱 쓰기를 막고 클라이언트 로그아웃을 시도하되, JWT 만료 전까지 남는 제한을 안내하며 완료 응답 전에는 보호되지 않은 세션이 남지 않도록 서버 정책을 점검하는 것이다.
7. **운영 담당과 복구 목표:** 권고는 탈퇴 실패 문의 담당자, 무료 범위에 맞는 백업 간격, 실측 복구 목표(RPO/RTO)를 정하고 합성 리허설 후 승인하는 것이다.

현 시점 권고: **운영 배포/마이그레이션/자동 탈퇴 활성화는 보류.** CI #78과 #79는 개발 브랜치 격리 검증이다. 운영 Storage 보호 함수 본문/동작, 실제 운영 백업 및 복원, 사용자 정책 결정이 남아 있다. 운영자가 별도로 승인하기 전에는 어떤 운영 반영도 하지 않는다.
