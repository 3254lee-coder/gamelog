# 회원 탈퇴 처리

개발 환경에서 먼저 001~008 마이그레이션을 순서대로 적용하고 테스트 계정 두 개로 본인 재인증, 다른 회원 답글 보존, 사진 업로드·정리와 인증 계정 삭제를 확인합니다. 004는 Supabase 관리 스키마에 트리거를 만들고, 005는 신고 빈도 제한을 추가하므로 대상 환경에서 마이그레이션 권한과 Auth·Storage 호환성을 확인해야 합니다.

NEXT_PUBLIC_MEMBER_SAFETY=true로 빌드하면 본인 확인과 요청 접수 화면이 활성화됩니다. 자동 처리는 서버 전용 WITHDRAWAL_PROCESSING_ENABLED=true 및 SUPABASE_SERVICE_ROLE_KEY가 별도로 필요합니다. 비밀키를 NEXT_PUBLIC 변수로 설정하지 마세요. 자동 처리 비활성 시 요청은 운영자 확인 대기로 남습니다.

인증 API는 토큰의 사용자 ID만 사용합니다. DB에 재인증된 탈퇴 요청이 존재해야 정리가 시작됩니다. 먼저 `lt_prepare_withdrawal`에서 개인정보와 작성 내용을 익명화하고 성장 기록·개체·좋아요를 정리해 이 단계를 커밋합니다. 그다음 Storage 사진을 지우고 Auth 계정을 삭제합니다. Auth 계정 삭제 시점에 오류가 발생하면 해당 Auth 삭제 트랜잭션만 롤백되고 요청은 남습니다. 앞서 커밋된 사전 익명화는 유지되므로 사진 정리나 Auth 삭제에 실패해도 원문은 복원되지 않으며, 사진 없이 익명화된 글만 남습니다. 계정은 남은 작업을 재시도할 때까지 로그인 상태로 남을 수 있고 사진 일부는 삭제된 상태일 수 있습니다. 사진 원본은 현재 백업하지 않으므로 Storage 삭제 후 복구할 수 없습니다. 소유자가 없는 이전 사진이나 경로가 일치하지 않는 사진은 운영자가 소유권을 확인해야 합니다.

007은 탈퇴가 시작되면 게시글·댓글·거북이·성장 기록·좋아요·신고·차단 관계의 추가 쓰기를 차단합니다. 처리 중인 기존 로그인 세션은 Auth 계정 삭제 전까지 유효할 수 있지만, 해당 세션으로 앱 데이터를 새로 쓰거나 바꿀 수 없습니다. 공개 게시글 읽기 및 Auth 사용자 메타데이터 접근은 세션이 남아 있는 동안 가능하므로 재시도는 지체하지 말고 운영자만 수행합니다.\n\n서버 요청 1회에서 최대 3묶음(묶음당 최대 100개)을 처리합니다. 초과하거나 네트워크·권한 문제가 생긴 요청은 서버에서 SUPABASE_URL과 SUPABASE_SERVICE_ROLE_KEY를 설정하고 다음 명령으로 재처리합니다.

```
node scripts/process-withdrawal.mjs <신청자-UUID> <프로젝트-ref> --process-verified-request
```

중단 시 서버 처리 플래그를 끄고 운영자 작업도 중지합니다. 접수·처리 중인 요청을 보존하며, 처리 시작 후 해당 회원의 신규 사진 쓰기는 제한됩니다. 이미 완료된 탈퇴는 웹 배포 롤백으로 복구할 수 없습니다.


## 백업·복구 제한

무료 플랜에는 자동 일일 백업이 없으므로, 배포 승인 후 Supabase CLI DB 덤프로 앱 스키마와 데이터를 암호화된 오프사이트 위치에 별도 보관합니다. CLI 덤프는 관리형 auth·storage 스키마를 제외하고, DB 백업에는 Storage 바이너리가 포함되지 않습니다. 이미지 파일은 별도 Storage API/CLI 사본과 경로·해시 매니페스트를 관리해야 합니다.

지원되는 Auth Admin API로 내보내고 재생성하는 방식은 사용자 메타데이터와 계정 속성을 제한적으로 옮기는 방법이며, 비밀번호 해시·세션을 복원하지 않습니다. 사용자는 재설정·재인증이 필요하고 새 Auth ID가 만들어지면 UUID를 참조하는 앱 데이터와 Storage 경로를 함께 매핑해야 합니다. 복구 범위는 운영 요금제 및 프로젝트 설정에 맞춰 확인하세요.

CI는 격리된 두 개의 로컬 Supabase 프로젝트를 순서대로 사용해 합성 DB 스키마·행, Auth 메타데이터 계정, Storage 객체를 복원합니다. 이 리허설은 운영 데이터에 접근하지 않으며 실제 운영 복구 가능성 또는 비밀번호 해시 복구를 증명하지 않습니다.
