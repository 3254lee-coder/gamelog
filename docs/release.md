# 운영 반영 전 확인

개발 브랜치에서만 작업합니다. 기존 SQL은 재실행하지 않습니다. 신규 기능은 NEXT_PUBLIC_MEMBER_SAFETY=true로 빌드할 때 활성화됩니다. 먼저 격리 환경에서 supabase/migrations/001_moderation.sql을 한 번 적용합니다. 신규 테이블의 기본 권한 부여, RLS, 기존 운영자 식별자, API 노출 설정을 확인합니다. 웹 코드에는 서비스 역할 키가 필요하지 않습니다.

신고는 글·댓글·답글·회원 대상이며 같은 신고자의 같은 대상 중복 등록을 고유 제약으로 막습니다. 처리 상태와 대상 식별자는 관리자 화면에서 조회합니다. 신고자 열 조회 권한은 클라이언트에 부여하지 않습니다. 차단은 개인 화면의 표시 필터입니다. 목록 페이지 수, 알림 및 공지 노출에 적용할 운영 정책을 확정한 뒤 기존 RPC까지 반영하십시오. 신고 대상의 존재 및 요청 빈도 제한도 운영 연동 전 검증 대상입니다.

탈퇴는 최근 비밀번호 인증을 거친 요청 접수 단계입니다. 요청은 회원별로 하나만 보관합니다. 운영에서 자동 삭제하기 전에 외래 키, Storage 경로 소유권, 다른 회원의 답글과 공용 콘텐츠 보존 방침을 확인합니다. 삭제 작업은 요청별 진행 상태를 기록하고 사진 정리와 계정 삭제를 단계별 재시도하도록 구현해야 합니다. 이 마이그레이션에는 기존 회원 삭제 작업이 없습니다.

승인 전에는 운영 DB에 SQL을 실행하거나 main을 병합하지 않습니다. 승인 후 DB와 웹을 별도로 배포하고 합성 테스트 계정으로 확인합니다. 기능 중단 시 플래그를 끄고 재빌드하거나 직전 Vercel 배포로 복원합니다. 신규 테이블은 운영 기록 보존을 위해 유지합니다.

인덱스는 실제 실행계획과 기존 인덱스를 먼저 확인합니다. 특히 댓글(post_id,created_at,id), 알림(recipient_id,read_at), 좋아요(post_id,user_id)의 고유성 및 성장 기록(tortoise_id,measured_on)을 확인합니다. 공개 게시글의 본문과 제목은 클라이언트에서 로드되므로 게시글별 검색 색인과 공유 메타데이터는 아직 별도 작업입니다.

개인정보처리방침에는 신고 사유·차단 관계·탈퇴 요청의 사용 목적, 처리 담당자, 보관 기간, 삭제 시점과 이의 제기 방법을 운영자가 확정한 내용으로 반영합니다. 약관 및 개인정보 문서 본문은 기존 문구를 유지했습니다.
